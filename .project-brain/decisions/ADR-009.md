# ADR-009 — Explicit ownership for receipt-created list rows
Status: ACCEPTED
Date: 2026-10-29

## Context
F15 authorizes deleting a receipt and the rows it created while retaining user plans and other receipts. Previous deletion guesses from timestamps and candidate links. Partial receipt rows can be linked during review, so neither time nor a link proves creation. F20 historical disappearance has not been reproduced and is not attributed to this defect.

## Decision
Add nullable planned_items.created_by_receipt_id, referencing receipts with ON DELETE SET NULL in schema v5. Write it atomically only when a receipt creates a new row. Existing plans linked during review keep their provenance. Approval updates the existing draft ID rather than replacing it. Delete explicitly owned rows only without remaining purchases; preserve shared rows and clear provenance through the FK. Include owned partial rows even before approval.

Old rows migrate with null (unknown) provenance. Never backfill from timestamps or links. Deleting legacy receipts removes purchases but retains unproven rows. Backups carry the nullable field; both modes insert receipts before planned items, validate same-list ownership and remap separate imports. Missing fields in older merge snapshots must not erase newer provenance.

Same-named partial rows from different receipts keep separate creators; automatic rules/AI matching excludes rows owned by another receipt. Background completion checks the pending draft and unchanged photos inside the same transaction as list creation/save. A deleted, approved or superseded draft cannot be resurrected. Merge also validates the resulting database ownership relation, including local-only retained rows, before commit.

## Alternatives and limits
Timestamp inference risks user data. Purchase links miss partial rows and conflate plans with receipt-created rows. A mapping table adds unnecessary state for one optional creator. The additive migration preserves old databases; older binaries cannot use schema v5 and rollback needs the original database/backup. No receipt money is committed before approval. No UI/model protocol change.
