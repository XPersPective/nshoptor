# ADR-010 — Locale-native presentation with canonical exact calculations
Status: ACCEPTED
Date: 2026-10-29

The user explicitly requires country-appropriate numeric handling in every published locale, not only TR/AR, and accepts a Latin-only limitation only if native support cannot be made safe. Existing intl/CLDR already supplies regional separators, grouping and default zero glyphs. Do not add a floating-point money library or maintain invented country conventions.

Keep DecimalFixed/BigInt and stored/AI-protocol decimal strings canonical ASCII. At manual numeric boundaries, normalize Unicode positional decimal digits and explicit punctuation/sign aliases before existing strict grouping and precision checks. Accept both native and ASCII keyboards. Never parse via double/NumberFormat.parse for monetary arithmetic. Shape every output digit, including fractions, according to the selected number locale; preserve the system-region vs UI-language distinction and explicit format overrides. CLDR default Latin digits in e.g. Japanese/Hindi are valid; do not force historical/algorithmic numerals or infer a country's rules from script alone.

OCR normalization is a temporary parsing view. Retain original captured lines/photos and identity/reconciliation evidence; do not replace product names wholesale or relax the model's canonical JSON schema. Digit support is not a claim that local OCR recognizes every writing system or that all real receipts are perfectly read. Live accuracy, approval and uncertainty controls remain release gates.

Sources consulted 2026-10-29: https://unicode.org/reports/tr35/tr35-numbers.html ; https://api.flutter.dev/flutter/package-intl_intl/NumberFormat-class.html . Installed intl data remains the implementation source of truth and must be exercised across the actual 71 supported locales.
